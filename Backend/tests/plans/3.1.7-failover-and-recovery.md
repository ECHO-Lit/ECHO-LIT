## Scope note

The RUP template describes Failover and Recovery Testing as ensuring that "the target-of-test can successfully failover and recover from a variety of hardware, software or network malfunctions with undue loss of data or data integrity". Its objective is:

> "Simulate the failure conditions and exercise the recovery processes (manual and automated) to restore the database, applications, and system to a desired, known state."

**Narrowing to this architecture.** ECHO has no failover cluster, standby node or replica, so there is nothing to fail *over to*. What this section tests is how a single-node deployment's components recover. There are four of them:

| Component | Role |
|---|---|
| API | One uvicorn process. It holds no state of its own. |
| Redis | Sessions on DB0, job records on DB1, the Celery broker on DB2. |
| Celery workers | Consume the queues and write job outcomes. |
| Local object store | Shared by the API and every worker. |

A "failover" in this deployment is a restarted container taking up where the old one stopped, or a remaining worker taking a dead worker's task. Both are exercised here.

| Source | Text | Role here |
|---|---|---|
| **RE-1** (§3.3, p. 27) | "The failure of a single worker shall not affect the availability of the API or the interface. Queued work shall continue on remaining workers." | Worker loss: the task is requeued and completed elsewhere, and the API stays available |
| **RE-2** (§3.3, p. 27) | "Job metadata and results shall be held in a durable, non-evicting Redis configuration with add-only persistence, so that ongoing and completed work is not silently lost under memory pressure. Failed tasks shall be retryable." | Redis loss, refusal and restart; the retry chain |
| **FR-4** exception flow (§3.1, p. 15) | "A worker error or time limit marks the job failed with an error message; a failed task may be retried; no partial result is exposed." | Time limits; convergence of every pipeline to a recorded outcome |
| **FR-14** (§3.1, p. 26) | "A running job can be canceled" · "Polling an unknown or expired job returns not found." | Cancelling a job whose worker is gone; lost jobs after a restart |
| **SAD UC-1** (§4) | Fail post-condition: "Job marked failed with an error; no partial/corrupt result is exposed." Extension: "a worker failure triggers a retry." | End-to-end oracle for the job pipeline |

**Items carried into this section.**
- From 3.1.1: "Redis connection loss mid-request and worker-crash-mid-job recovery (3.1.7)", and "Backup / restore / disaster recovery — belongs to section 3.1.7".
- From 3.1.5: "failure injection under load", and "worker or Redis failure mid-load".

All of them are covered below.

**Interpretation of RE-2's "Failed tasks shall be retryable".** This was decided at planning time. The requirement is met in two ways: by the automatic retry chain for transient failures, and by resubmitting the identical request, which the per-file cache makes cheap. There is no user-facing retry endpoint, and building one is not part of this section; that is recorded as OBS-31.

## Technique

The template's failure conditions map onto this architecture as follows.

| Template condition | ECHO realisation | Cases |
|---|---|---|
| Power interruption to the client | The browser holds no job state. A job runs to its outcome whether or not anyone is polling it, and the session cookie reaches it afterwards. | FO-09, FO-13 |
| Power interruption to the server | A worker process dies holding a task. The Redis process restarts, with and without its append-only file. | FO-20, FO-21, FO-30, FO-92; FO-13, FO-14, FO-93 |
| Communication interruption | Redis becomes unreachable, entirely or one database at a time. The broker is unreachable at dispatch. | FO-01 to FO-12, FO-61, FO-90, FO-91 |
| Interruption of storage (DASD) and controllers | The object store fails transiently or persistently. A full Redis refuses writes. Two writers write one object at once. | FO-11, FO-27, FO-28, FO-57, FO-59, FO-60, FO-78 |
| Incomplete cycles | A worker dies mid-batch. A task hits the soft or hard time limit. A chord stage fails. A final failure write cannot land. A task is redelivered for a finished job. | FO-22 to FO-26, FO-30, FO-32, FO-40 to FO-64 |
| Invalid database pointers or keys | A cache pointer leads to a damaged object. Sub-keys sit under `job:*`. A session key has the wrong type. Pointers are lost with an empty restart. | FO-12, FO-14, FO-47, FO-70 to FO-77 |
| Invalid or corrupted data elements | Truncated or wrong-shape JSON in a cache. An unreadable job record. A damaged FR-10 plan. | FO-47, FO-58, FO-70 to FO-79 |

**How failure is injected.** A new module, `tests/_faults.py`, owns one `fakeredis.FakeServer` that plays the Redis process. Every client the application holds is resolved through the harness on every call:

- the API's three asyncio clients;
- the worker's two synchronous clients;
- one asyncio client per (thread, event loop), so a worker running on `tasks._loop` in another thread shares data with the API.

That makes three failures exact and cheap:

- **`outage()`** sets `FakeServer.connected = False`. Every client, pipeline and WATCH raises `redis.exceptions.ConnectionError`, and the *same* client objects work again afterwards, as a redis-py pool does. FO-01 verifies this before anything relies on it.
- **`restart(persist=…)`** swaps in a new server process. With `persist`, the new server is repopulated key by key with `DUMP`/`PTTL`/`RESTORE`, the way Redis replays its append-only file. Connections to the old process die. Without `persist`, the new server starts empty.
- **`FaultyRedis`** is a delegating proxy, in the style of 3.1.4's `CountingRedis`. It refuses chosen commands, for example an OOM refusal under `noeviction`, or a single unreachable database.

**How worker failure is injected.**
- For the two failures Celery handles *outside* the task (worker lost, hard time limit), the cases build Celery's own `celery.worker.request.Request` from a `celery.contrib.testing.mocks.TaskMessage` and call `on_failure` / `on_timeout` on it. The decision to requeue or acknowledge is therefore Celery's, made under ECHO's real configuration.
- For everything inside a task, the real task runs eagerly with `.apply()`. Celery's eager mode re-executes a `self.retry()` synchronously, so a whole retry chain runs in one call.
- A worker dying mid-call is modelled as a `BaseException` that no `except Exception` clause catches. From the job record's point of view that is exactly what a SIGKILL looks like: no handler runs.

**Under load.** `run_with_faults` extends 3.1.5's harness. It runs virtual users, each its own session, against the real ASGI app with `raise_app_exceptions=False`, so every response is what a browser would receive. A fault fires on a schedule. `ResilientWorker` is 3.1.5's `SimulatedWorker` with the real task's recovery behaviour: it retries on a Redis error, and `kill(n)` stops *n* consumers mid-job and requeues their envelopes, as `reject_on_worker_lost` does.

**Every guard was first observed failing** against the unfixed application. `app/` was stashed and the five new modules were run: 124 failed and 35 passed, where the 35 are the characterisation cases listed in Execution Results. Pre-fix evidence is quoted per defect under Findings.

## Oracles

| Oracle | Observation method | Success indication |
|---|---|---|
| **Fail cleanly** | The response a browser receives (`raise_app_exceptions=False`) | 503, a JSON `detail`, `Retry-After`, and `Access-Control-Allow-Origin` for the calling origin |
| **Resume without intervention** | The same client objects and the same cookie after the fault | Same `sid`, same audio and job records, and in-flight jobs reach `success` |
| **No loss on restart** | Keys and TTLs across `restart(persist=True)` | Every record returns; TTL within 2 s of its pre-restart value |
| **Convergence** | The job record after the failure path | A terminal state with an error `code` and a non-empty `message`; never left unfinished |
| **No partial result** | `result_url` and `GET /jobs/{id}/result` | `result_url` is null and `/result` returns 409 for a failed job |
| **Requeue vs acknowledge** | The recorded `on_ack` / `on_reject(requeue)` of a real Celery `Request` | Worker lost: `reject(requeue=True)`, no failure written. Hard limit: acknowledged, job failed |
| **No wasted work** | A must-not-run stand-in for each task's work | Never called for a finished job |
| **Cache repair** | Model call count and the cache object after a damaged read | The damaged entry is recomputed, rewritten, and served to the next job |
| **Under load** | Every response's status and time window | 503s only inside the fault window, no other failures, every accepted job succeeds, every user resumes |

## Special Considerations

**1. The template's intrusiveness warning does not apply.** The template notes that "recovery testing is highly intrusive" and should run "after hours or on an isolated machine". Every fault here is injected in-process, into objects owned by one test, so the section runs on every change like the rest of the suite. This is the house convention since 3.1.1.

**2. A refused connection, not a hung one.** `FakeServer.connected = False` models a Redis that refuses connections. A Redis that hangs would make each call wait `socket_timeout=5` s (`core/redis.py`) before failing. It fails with `TimeoutError`, which is a `RedisError`, so it takes the same handler and gets the same 503, but a request pays the timeout first. The handler path is covered; the latency of a hung dependency is not.

**3. Timings are ordered, and the order is enforced.**

| Timing | Seconds |
|---|---|
| Soft limit | 3 300 |
| Hard limit | 3 600 |
| Broker visibility timeout (hard + 600) | 4 200 |
| Stale-job cutoff (visibility + 1 800) | 6 000 |
| Reaper sweep interval | 300 |

A task lost with its worker is therefore redelivered, about 70 minutes after it started, before the reaper would give up on its job at 100 minutes. A stale cancel requested by the job's own owner uses the shorter cutoff, the hard limit: a job silent that long cannot still be running its last step. `Settings` refuses any configuration that breaks the order (FO-34).

**4. Main process vs pool children.** The hard-time-limit handler runs in the worker's *main* process, via Celery's `task_failure` signal. That process runs Celery's callbacks and has no event loop, and the redis.asyncio clients belong to the pool children's loops. So the handler writes through a synchronous client with its own WATCH transaction (`recovery.finish_failed_sync`), the same pattern as the existing heartbeat receiver.

**5. The reaper only acts on a job it can prove is unfinished and untouched.** A `queued` job with no error is never reaped, however old, because its broker message is durable and a worker will take it. The transition re-checks staleness inside its WATCH transaction (FO-46). A Redis error fails the sweep having changed nothing (FO-49), the same fail-safe rule as 3.1.5's dataset sweep.

**6. `/audio/{id}/variant` runs `fr7_render_variant` with no job record.** The terminal-state skip therefore treats a *missing* record as "run" for that one task and as "skip" for every other task (FO-32).

**7. Runtime.** The five modules take about 33 s in total. The four load cases take about 4.5 s each; everything else runs in well under a second per case.

## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.7 is covered for every reliability requirement the SRS states.** Before this pass no case had injected a failure of any kind. The section now fails each component the deployment runs on, and checks that every failure ends in a known, recorded state. That covers Redis (unreachable, refusing, restarted with and without its data), the workers (lost, timed out, retried, redelivered), the object store (failing, concurrent) and the caches (damaged). It runs the three worst of those failures under the 3.1.5 workloads.

Four defects are High:
- a Redis blip stranded every user (BUG-50);
- abandoned jobs could not be ended by anyone (BUG-54);
- pipelines stalled silently (BUG-55);
- one damaged cache file failed every matching job (BUG-57).

All four were found by predicting from the code and then confirmed by failing guards. Every guard is in the suite.

Deliberately excluded, with justification:

| Excluded | Reason | Owner |
|---|---|---|
| Worker topology and durability configuration (OBS-33, OBS-34) | Deployment configuration | **3.1.8** |
| A *hung* (rather than refused) Redis | Same handler path; only the 5 s socket timeout differs (Special Consideration 2) | — |
| Multi-node failover | No second node exists in the architecture | — |

**Carried forward:** OBS-33 and OBS-34 to **3.1.8**, joining OBS-24 there.
