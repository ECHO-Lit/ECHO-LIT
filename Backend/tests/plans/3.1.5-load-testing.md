## Scope note

The RUP template defines Load Testing as a performance test that "subjects the target-of-test to varying workloads to measure and evaluate the performance behaviors and abilities of the target-of-test to continue to function properly under these different workloads", with the objective:

> "Verify performance behavior time for designated transactions or business cases under varying workload conditions."

Section 3.1.4 profiled one transaction at a time. This section asks what happens when many run at once: many users, one user doing something heavy while others work, many workers on one batch, and state accumulating over time.

| Source | Text | Role here |
|---|---|---|
| **PE-1** (§3.4, p. 27) | "…shall respond within 500 ms on average under normal load." | Budget under the average workload |
| **PE-2** (§3.4, p. 27) | "The asynchronous pipeline shall process multiple audio files concurrently across worker queues; batch throughput shall scale approximately linearly with the number of available workers up to hardware limits. Submitting a batch of many files shall not block the interface." | Worker scaling; non-blocking under background load; client burst |
| **PE-3** (§3.4, p. 28) | "The system shall accept audio up to 100 MB and 10 minutes per file. … A 24-hour expiry on transient objects shall bound cumulative storage growth." | Capacity limits on every upload path; bounded growth of every store |
| **US-3** (§3.2, p. 26) | "…the interface shall remain fully interactive while computation proceeds in the background." | Pollers under background load |
| **RE-2** (§3.3, p. 27) | Job metadata held in a "durable, non-evicting Redis configuration" | Why growth must be bounded by expiry rather than eviction |

**Inherited item.** 3.1.3 carried **OBS-14** (the audio type check duplicated verbatim in two components) here. It is resolved below.

## Technique

The template's bullets are realised as follows.

**"Use tests developed for Function or Business Cycle Testing. Modify data files to increase the number of transactions or the tests to increase the number of times each transaction occurs."** `tests/_load.py` defines a **virtual user**: its own `AsyncClient`, therefore its own session cookie — a distinct session to the API — running the researcher's core loop against the real ASGI application: establish a session, upload a clip, then repeatedly submit a job, poll it to completion, fetch the result and pause. Behind the broker boundary a **simulated worker** receives exactly the envelope `send_task` would have published and advances the job through the real `JobRepository` and the real object store after a fixed service time. The whole control-plane lifecycle is therefore under load; the model's own cost — which PE-1 explicitly excludes — is a parameter.

**Workload shapes** (the template's "average vs peak vs sustained-peak"):

| Profile | Users | Duration | Think | Poll interval | Service time | Workers |
|---|---|---|---|---|---|---|
| AVERAGE | 5 | 5 s | 0.5 s | 0.2 s | 0.10 s | 4 |
| PEAK | 25 | 5 s | 0 | 0.05 s | 0.05 s | 8 |
| SUSTAINED | 25 | 15 s | 0 | 0.05 s | 0.05 s | 8 |

The real client polls every 1–2 s with back-off to 5 s (`use-job-query.ts`, `lib/jobs.ts`). AVERAGE already polls five times faster; PEAK removes think time and polls twenty times faster than any human cohort — deliberately harsher than reality. SUSTAINED holds PEAK three times as long, so a defect that only accumulates shows as drift.

**"Background workload on the server"** (template Special Considerations). Ten pollers — ten open dashboards — measure `GET /jobs/{id}` alone, then again while *another* user does the heaviest thing the API accepts. The pollers are compared against their own baseline from the same case, so host speed cancels out, and `loop_lag_probe` (3.1.4) checks the loop never stalled.

**Worker scaling.** `execute_batch_item` runs on 1, 2 and 4 OS threads, each with its own event loop and Redis client over one shared store, exactly as `orchestrate_batch` fans items out to N Celery worker processes. The model call is replaced by a fixed, GIL-releasing cost. This establishes that the **worker code** has no serialisation point — no shared lock, no contended transaction that starts failing, no per-job state only one item may touch. Hardware throughput of the model itself is a property of the deployment's accelerators.

**Capacity and growth.** Every tier that holds user data is checked for a bound: Redis by TTL under sustained load, the object store by its hourly sweep, custom datasets by the new sweep keyed on session expiry.

**Client burst.** A route stand-in holds each request open until the case releases it and records the peak number in flight — the load one researcher's browser puts on the API.

**Every guard was observed failing first**, against the unfixed code, by stashing product changes and re-running the new modules (quoted in Findings).

## Special Considerations

**1. Load generator and target share one core.** The virtual users' httpx clients run on the same event loop as the application. At PEAK, most of the loop's time is the *clients'* work, so peak latencies here are pessimistic — a remote user's server-side latency would be lower. The AVERAGE figures are the ones PE-1 is asserted against without reservation.

**2. PEAK's upload row is a start-up artifact.** All 25 users upload in the same instant when the run begins and never again. PE-1 bounds only *normal* load, so LT-02 asserts the 500 ms mean for the calls a running job repeats (submit, poll, result) and a < 1 s p95 for every endpoint including that burst. The burst also surfaced BUG-47 (3.1.4): with ffprobe first it averaged 656.8 ms and the loop stalled 338 ms; with libsndfile first, 232 ms and 42 ms.

**3. fakeredis is thread-safe enough to be the shared store — verified, not assumed.** Four threads each performing 200 `WATCH`/`MULTI` increments on one key, with a yield between read and write, ended at exactly 800. That is why the worker-scaling cases can use per-thread clients over one `FakeServer`, and why their verdicts concern ECHO's code rather than the fake.

**4. The dataset lock is per process.** BUG-36's `asyncio.Lock` serialises writers inside one API process, which is the deployed topology (`docker-compose.yml` runs a single uvicorn process). Several uvicorn workers sharing `uploads/` would need a cross-process lock; recorded as OBS-29 rather than built for a topology that does not exist.

**5. The dataset sweep fails safe.** It keys on `sess:{sid}:meta` existing in the session database. A Redis error propagates and fails the run (LT-34), so an outage can never be read as "every session expired". RE-2 requires append-only persistence, so a Redis restart does not lose session keys either.

**6. Runtime cost.** The seven backend modules of 3.1.4/3.1.5 add ~70 s to a full run; the largest single case is LT-13 (~16 s), where ten pollers fair-share the loop with ~1 500 multipart chunks of a 96 MB upload. That is the case's point, so it was not shortened.

**7. Reverse-order runs must be offline.** The order-independence run found a test that downloaded a real model when run late (see TEST-01). Every backend run for this section now sets `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`, so a regression of that kind fails fast instead of reaching the network.

## Findings

### Defects

| ID | Sev | Status | Location | Finding and resolution |
|---|---|---|---|---|
| **BUG-43** | Medium | **Fixed** | `services/custom_dataset_service.py:408`, `worker/tasks.py`, `core/celery_app.py` | **Custom datasets were never deleted — PE-3's storage bound did not hold for them.** They live on disk under `uploads/sessions/`, outside `STORAGE_LOCAL_ROOT`, so the hourly `cleanup_expired_local_objects` never saw them; and `cleanup_session_datasets` — whose own docstring says "called when session expires" — had exactly one caller, the manual `POST /dataset/cleanup`. Every dataset ever uploaded stayed on disk after its session's Redis state expired. Pre-fix: LT-32…LT-34 could not import a sweep because none existed. **Resolution:** `cleanup_expired_session_datasets`, run hourly by beat on the `cpu` queue, removes the tree of each session whose `sess:{sid}:meta` key is gone — keyed on the session's own lifetime rather than file age, so it never deletes under a session in use, and fails safe on a Redis error. The workers and scheduler already mount `./Backend/uploads` (`docker-compose.yml`), so the sweep sees the same tree the API writes. |
| **BUG-46** | Medium | **Fixed** | `Frontend/src/components/panels/AudioDatasetPanel.tsx:259`, `hooks/use-layer-probes.ts:133`, `EmbeddingPanel.tsx:349/381/414`, `EmbeddingContext.tsx:108`, `DatasetEdaView.tsx:178`, `ScalersVisualization.tsx:163/193/222`, `AudioUploader.tsx:53` | **One browser sent an unbounded burst.** Ten call sites materialised whole datasets with `Promise.all(files.map(materializeAudio))` — 144 simultaneous POSTs for RAVDESS, each making the API probe, hash and copy a file on its shared thread pool — and the drop zone started every dropped upload (up to 100 MB each) at once. Over HTTP/2 the browser's six-connection cap does not apply. When one request failed, `Promise.all` rejected but the rest kept running for nothing. Pre-fix: LC-05 measured **6 concurrent uploads** against a limit of 2; LC-04 found no bounded helper; LC-07 found the unbounded pattern at every site. **Resolution:** `src/lib/concurrency.ts` `mapWithConcurrency` (order-preserving, stops scheduling after the first failure) and `materializeAll` (limit 4) in `lib/jobs.ts`, used at every site; the uploader runs two at a time and one failure no longer stops the queue (LC-06). The J-Lens Lab already batched in eights and is unchanged. |
| **BUG-48** | Medium | **Fixed** | `app/core/storage.py:70-74` | **Concurrent workers could fail legitimate writes with "Object key escapes storage root".** On Windows, `Path.resolve()` intermittently returns the `\\?\C:\…` extended-length form for a path while other threads create files in the same directory. That form has no `C:\…` ancestors, so the containment check rejected a valid key, and a batch item failed with `StorageError` — which Celery then retried. **Found by LT-21, not predicted:** two of four cases failed on every run of the module until diagnosed; an instrumented run captured `got=\\?\C:\Users\…\cache-items\312a58…json` for a key inside the root. **Resolution:** the prefix is removed after `resolve()` — kept for its symlink protection — for both the root and the candidate; UNC paths and real escapes are unaffected (LT-24). Linux containers do not produce the prefix, so the deployed workers were not exposed; Windows development runs and this suite were. |

## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.5 is covered for every load requirement the SRS states.** Before this pass no case had submitted a job under concurrent load, run more than one worker, varied the workload, or looked at what accumulated. Two defects here were found by the suite rather than predicted — **BUG-48** by the worker-scaling case, and **TEST-01** by the order-independence run — and the load cases re-confirmed four of 3.1.4's fixes at the level PE-2 actually describes: other users' requests.
