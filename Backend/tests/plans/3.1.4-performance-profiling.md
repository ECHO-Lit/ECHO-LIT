## Scope note

The RUP template defines Performance Profiling as a test in which "response times, transaction rates, and other time-sensitive requirements are measured and evaluated", with the objective:

> "Verify performance behaviors for designated transactions or business functions under the following conditions: normal anticipated workload [and] anticipated worst case workload."

This section profiles **one transaction at a time**: what a single request, a single job or a single statistic costs, and where that cost is paid. How the system behaves when many run at once is Section 3.1.5 (Load Testing), which reuses the instruments built here.

The authoritative requirements are the SRS's own performance clauses, extracted with `pdftotext -layout "docs/Group 16 - AudioLens SRS.pdf" -`:

| Source | Text | Role here |
|---|---|---|
| **PE-1** Response time (§3.4, p. 27) | "Control plane API calls that do not perform inference (upload acknowledgment, job creation, status polling, result retrieval) shall respond within 500 ms on average under normal load. Job submission shall return within this budget regardless of the size of the underlying computation." | The primary budget |
| **PE-3** Capacity (§3.4, p. 28) | "…accept audio up to 100 MB and 10 minutes per file. Long-running tasks are bounded." | Per-request memory, worker compute bounds |
| **US-3** Feedback (§3.2, p. 26) | "Every long-running operation shall provide immediate acknowledgment (within 500 ms), a visible progress indication…" | Client acknowledgment latency — **carried from 3.1.3** |
| **FR-4** AC-1 (p. 15) | "Submitting a batch returns a job_id within the control plane latency budget" | **Carried from 3.1.2** |
| **RE-3** (§3.3, p. 27) | "analytical results shall be reproducible for identical inputs and configuration" | Constrains any speed-up of a statistic |

**Inherited items.** 3.1.2 carried FR-4's submission latency here. 3.1.3 carried the US-3 500 ms acknowledgment budget and the `XMLHttpRequest` upload-progress upgrade (its BUG-22 was fixed only to an indeterminate indicator, because Fetch reports no upload progress). All three are closed in this section.

**Not in scope.** Model inference time is excluded by PE-1's own wording ("calls that do not perform inference"). Worker cost is profiled for computation that is the product's own code — FR-10's statistics — with the model call outside the measurement.

## The state this section found

`Backend/tests/test_performance_load.py` (280 lines, 13 cases) was the only performance coverage in the repository. It **could not detect a performance defect in ECHO**:

- `test_model_inference_performance_whisper` patched `transcribe_whisper`, made the mock `time.sleep(12.0)`, then asserted the call took ≤15 s — timing its own sleep. `test_wav2vec2_inference_performance` did the same with 28 s against a 30 s limit, **and patched the wrong function** (`transcribe_whisper` for a wav2vec2 case).
- The memory and CPU cases called the same mock in a loop and asserted process totals no real regression would move.
- The thresholds had been **raised to fit observed slowness**: `MAX_API_RESPONSE_TIME = 5.0  # Increased from 2.0 to 5.0 seconds (your system: ~4.1s)` — ten times the SRS budget, with the reason in a comment.
- None carried the `performance` marker that `pytest.ini` registers.

`test_session_cookie.py::TestSessionCookiePerformance` asserted ten sequential `/session` calls finished under 5 s, and `test_session_memory_efficiency` measured no memory at all. `run_tests.py performance` passed `--benchmark-only` to a plugin that is not installed, and defined a `PERFORMANCE_BENCHMARKS` dict nothing read.

All of it is removed; see "Vacuous tests removed".

## Technique

The template's bullets are realised as follows.

**"Use Test Procedures developed for Function or Business Cycle Testing."** Every case drives the real ASGI application through `httpx.AsyncClient(app=app)` — the same harness 3.1.2 used — or calls the real service function. No route, repository or statistic is replaced; only the things PE-1 excludes (the broker, the model) or that this host cannot represent faithfully (see Oracles) are stood in for.

**"Modify data files to increase the number of transactions or the scripts to increase the number of iterations."** Each budget is asserted on the **mean of repeated samples** (5–50 per case), because PE-1 says "on average". Size-dependence is profiled at the limits the API itself enforces: `audio_ids` at its `max_length=200`, FR-10 at `max_items_per_group=2000` and `n_bootstrap=20000`, FR-7 at `MAX_GRID_VARIANTS=60`, uploads at the 100 MB / 10 minute boundary.

**"Scripts should be run on one machine … with a single transaction."** Three instruments, in `tests/_perf.py`, each measuring a different property:

1. **Wall-clock budgets** against the SRS numbers.
2. **Event-loop lag.** The API is one asyncio process; a synchronous call inside an `async def` route freezes *every* user on that worker, not only the caller. `loop_lag_probe` runs a ticker on the loop the app shares with the test and records its worst wake-up delay. The route's expensive dependency is replaced by `blocking_cost(0.25)` — a stand-in of **fixed, known** duration — so the verdict (<100 ms: off the loop; ≥250 ms: on it) depends on *where* the work runs, not on how fast this host is.
3. **Accounting.** A Redis round trip costs microseconds on fakeredis and a network hop in production, so N+1 access is asserted as a command count (`CountingRedis`). Upload memory is asserted as the largest single chunk a route reads from an `UploadFile`.

**Client acknowledgment (US-3).** 3.1.3 excluded the 500 ms number because a wall-clock assertion under jsdom measures the runner. It is owned here by **removing the network from the question**: the fetch stand-in holds the request open, and the case asserts the acknowledgment is rendered *while no response exists*. An acknowledgment that precedes any server response is bounded by one render; the server half of the budget is PE-1.

**Every remediation was observed failing first.** Pre-fix evidence was captured against the unfixed code — before the change, or by stashing `Backend/app` / `Frontend/src` product changes and re-running the new modules — and is quoted in the Findings table.

## Special Considerations

**1. What an in-process measurement is.** Client and server share one event loop and one core. A latency here is the server's processing time *plus* the httpx client's, with no network — a conservative upper bound on server cost and a lower bound on what a remote user sees. The budgets are asserted with one to two orders of magnitude of headroom (4–111 ms against 500 ms), so a failure is a regression, not noise.

**2. Windows timer resolution.** `asyncio.sleep(0.005)` on Windows wakes on the ~15.6 ms system tick, so an idle probe reads up to ~16 ms of "lag". The 100 ms limit sits far above that floor and far below the 250 ms stand-in; PP-15 and PP-15b calibrate both sides in every run.

**3. The stand-in's duration is the point.** A `blocking_cost` stand-in is not a mock of the product: it replaces an *external* cost (a broker publish, an ffprobe spawn, a cold scan of 144 files) with one of known duration so the oracle can say where it was paid. Where the blocking behaviour is ECHO's own code — `resolve_file`'s retry sleep — the real code runs (PP-24).

**4. ffprobe on this host versus the API image.** `probe_audio` measured **77.6 ms** per call here (a process spawn) against **0.8 ms** for `soundfile.info`. `Backend/Dockerfile` installs ffmpeg on workers only ("the API never decodes audio"), so the deployed API already took the libsndfile fallback. BUG-47 reorders the two so development matches production; the event-loop cases use a 50 ms stand-in per file, below either figure's worst case.

**5. RE-3 and the bootstrap rewrite.** BUG-41's fix changes floating-point summation order: a resample's mean is computed as Σ(block sums)/Σ(block sizes) instead of the mean of a concatenation. The **random draw sequence is identical** — the same `rng.integers` calls, in the same order — so intervals agree to 1e-12 and p-values exactly on continuous data (PP-28). On degenerate data with exact ties, a resample whose centred mean lands exactly on |point| could in principle round differently and move a p-value by 1/`n_boot`; the result remains deterministic for identical inputs, which is what RE-3 requires. All 54 `test_fr10_*` cases pass unchanged.

**6. Celery from worker threads.** BUG-35's fix publishes through `asyncio.to_thread`. Celery's `send_task` acquires a producer from a pool per call and is safe to call from threads; `revoke_async` keeps one `revoke` call per task id so 3.1.2's recording broker still observes each one.

**7. The heartbeat key moved.** BUG-39 replaces per-worker `worker-heartbeat:{host}` keys with one sorted set, `worker-heartbeats`, written through `app/core/heartbeat.py`. That module lives in `app.core`, not `app.worker`, so `/health` keeps 3.1.2's control-plane import purity. `scripts/queue-status.sh` read the old keys with `KEYS` and was updated to `ZCOUNT`. A rolling deploy briefly reports zero workers until every worker has run the new code — the API and workers ship from one image, so this is a restart artifact, not a steady state. The worker's hostname is now read from `Heart.eventer.hostname`; the old fallback `str(sender)` produced an object repr with a memory address, a new member on every restart (the ops script's own comment complained of it).

**8. A GC pause is not the product.** Two full-suite runs failed a background-load case (in 3.1.5) with a single ~214 ms stall that never occurred in isolation; poll latency itself was normal. Diagnosis: a full-generation garbage collection over the heap ~600 earlier tests had built. `loop_lag_probe` now collects and `gc.freeze()`s pre-existing objects for its window. Two consecutive full runs then passed. The mitigation is in the instrument, not in any threshold.

**9. Client cases need no timing.** PF-01/02 hold the POST or the first GET open indefinitely. What is asserted is state, not duration, so the cases cannot flake on a slow runner.

| **BUG-41** | **High** | **Fixed** | `services/fairness_metrics_service.py:317-323` | **FR-10's unpaired bootstrap cost 14 s per gap at the API's own limit.** Every resample rebuilt a Python list of block keys and concatenated Python lists of floats, making it O(`n_boot` × items) in interpreted code. Measured on this host: 1.2 s at 100 items per group, 9.9 s at 1 000, 32.6 s at 3 000 — **per metric, per non-reference group**. PP-25: 14.29 s → 0.28 s. PP-26: 2.06 s at 20 000 resamples. Equivalence to the verbatim pre-fix code guarded by PP-28. |
| **BUG-42** | **High** | **Fixed** | `api/routes/jobs.py:188-198` | **Result retrieval breached PE-1 on its own.** `GET /jobs/{id}/result` parsed the stored JSON and returned the dict, so FastAPI re-encoded every value on the event loop. A maximal 200-item embedding result (~3 MB) took **574.2 ms mean** (PP-05, pre-fix, n=5). Found by the budget case, not predicted. **Resolution:** the stored object *is* the response document (`put_json` wrote it), so its bytes are returned directly as `application/json`. 574 → 59 ms. |
| **BUG-36** | **High** | **Fixed** | `api/routes/dataset_management.py:106-117`, `services/custom_dataset_service.py:119-175` | **A custom-dataset batch upload froze the whole API — the literal PE-2 violation.** Per file, on the event loop: write the bytes, run ffprobe (77.6 ms here), read the entire metadata JSON and write it back. A 20-file batch stalled **every user's requests** for its whole duration; the rewrite-per-file also made an n-file batch O(n²) in bytes written. Pre-fix: PP-21 observed a **417 ms** stall for five files; 3.1.5's LT-10 observed **1 604 ms** for twenty. **Resolution:** files stream to a staging directory; one `add_files_to_dataset` call moves, probes and records the whole batch **off the loop** with a **single** metadata write. Moving work off the loop *creates* a lost-update race the loop had been hiding, so the batch — and the manifest and delete routes that also rewrite the document — hold a per-(session, dataset) `asyncio.Lock` (guarded by 3.1.5's LT-14/LT-15). |
| **BUG-35** | Medium | **Fixed** | `routes/jobs.py:150,225,227`; `routes/analyses.py:136,246,287,289`; `routes/models.py:53,111`; `routes/upload.py:248` | **Broker calls ran on the event loop.** `celery_app.send_task` is a synchronous network publish and `control.revoke` a synchronous broadcast; nine call sites made them inside `async def` routes. A congested or reconnecting broker — exactly when it is slow — froze every in-flight request. Pre-fix, with a 250 ms broker: PP-16…PP-20 all failed (PP-19 **292 ms**, PP-20 **245 ms** stalls; the three submission cases' magnitudes were not retained in the captured output). **Resolution:** `send_task_async` / `revoke_async` in `core/celery_app.py`, both `asyncio.to_thread`. |

| **BUG-37** | Medium | **Fixed** | `routes/dataset_management.py:109` | **The dataset upload path had no size or duration limit and read each file whole.** `await file.read()` held up to the whole file per upload in the API process, and neither PE-3 limit was enforced — `POST /upload` had both, this path neither. | **BUG-44** | Medium | **Fixed** | `Frontend/src/hooks/use-job-query.ts:87` | **The Run button re-enabled after the server accepted the job.** `isRunning` was derived from the first status response, so for one full GET round trip after the 202 the mutation was no longer pending and no status existed: the button re-enabled, the progress indication vanished, and a second click submitted a duplicate 10–30-minute job. ## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.4 is covered for every performance requirement the SRS states.** Before this pass the performance suite could not fail for a reason inside ECHO. It now binds every PE-1 transaction to the SRS number against the real application, proves submission independent of computation size structurally, and bounds FR-10's statistics at the largest configuration the API accepts.

Three High-severity defects were fixed. **BUG-42** — result retrieval over PE-1's budget on its own — was found by the budget case rather than predicted, and **BUG-49** was found by the client cases. That is the argument for asserting the SRS number directly instead of a threshold chosen to pass.

Deliberately excluded, with justification:

| Excluded | Reason | Owner |
|---|---|---|
| Behaviour under many simultaneous users | By definition Load Testing; this section's instruments are reused there | **3.1.5** |
| Browser rendering cost of plots and the bundle | jsdom has no layout, paint or WebGL; recorded as OBS-20/OBS-21 with measurements | Real-browser profiling pass |
| Security properties of the new routes' behaviour | Not a performance concern. *Status after 3.1.6:* partly covered — SEC-06, SEC-22, SEC-23 (`3.1.6-security-testing.md`) | **3.1.6** |

**Carried forward:** OBS-19 to a **3.1.3 error-presentation follow-up** · OBS-20 to a **UX decision** on lazy-loading panels · load behaviour of every fix here to **3.1.5**.
