## Scope note

Function testing verifies requirements that trace directly to use cases, business functions and business rules, exercising the target through its external interface with valid and invalid data and observing the result. For ECHO the external interface is the **HTTP API**: the product's own UI is a client of it, and every use case in the SAD is realised through it.

Two authoritative sources define what the functions *are*:

| Source | Role here |
|---|---|
| `docs/Group 16 - AudioLens SRS.pdf` §3.1 (pp. 11–25) | **Business functions and rules** — FR-1…FR-14, each with Actor / Trigger / Preconditions / Inputs / Processing / Outputs / Exception flows / **Acceptance criteria** |
| `docs/Group 16 - AudioLens SAD.pdf` §4 (pp. 7–10) | **Use cases** — 3 actors (ML Researcher/Practitioner, Dataset Curator, System Administrator) and 4 use-case realizations |

Extract the SRS criteria with `pdftotext -layout -f 10 -l 26 "docs/Group 16 - AudioLens SRS.pdf" -`.

**Requirements outside this section's scope.** Requirements not yet implemented are excluded from this section entirely, by decision: they will be tested in their own pass once built. Their absence here is a scoping decision, not a coverage gap, and this document makes no claim about them either way. The traceability matrix below is therefore complete **with respect to implemented functionality**.

## Technique Objective

Exercise each business function through its external interface — navigation, data entry, processing and retrieval — with valid and invalid data, to observe and log that expected results occur for valid input, that the appropriate error is returned for invalid input, and that each business rule is applied.

---

## Technique

The RUP template prescribes three checks. Each is realised as follows.

**"The expected results occur when valid data is used."** Every endpoint under test is driven through the real ASGI application with a real session cookie, and the response is asserted against the requirement's stated Outputs — not merely against a success status. FT-01, for instance, asserts that duration, sample rate, channels and SHA-256 are the *probed* values, which an implementation that echoed the request could not produce.

**"The appropriate error or warning messages are displayed when invalid data is used."** Invalid data is supplied in the shapes a real client produces: wrong extension, wrong content type, oversized payload, malformed CSV, wrong encoding, absent required field, unknown identifier, an identifier belonging to another session, and cross-field contradictions. **Every assertion checks the exact `detail` string, never a status code alone.** This is not stylistic: the datasets router is mounted at the application root with `/{dataset}/metadata`, so almost any mistyped two-segment GET returns *some* 404. A status-only assertion in this codebase can pass for entirely the wrong reason — FT-75 exists to pin that behaviour down.

**"Each business rule is properly applied."** Rules are asserted at the layer a user meets them. `test_layer_probe_schema.py` already asserts the `JobCreateRequest` rules against the Pydantic model directly; those tests would still pass if a route stopped calling the validator. FT-79…FT-82 assert the resulting HTTP status and message instead.

**Traceability discipline.** Each case names the FR and, where the SRS states one, the acceptance criterion it verifies. Criteria that span tiers are recorded as such rather than claimed (see FT-69).

## Oracles

| Oracle | Observation method | Success indication |
|---|---|---|
| **Response contract** | Status code plus the full response body | Body matches the requirement's stated Outputs, including derived fields and legacy aliases |
| **Exact error message** | `response.json()["detail"]`, compared verbatim | The documented message, so a regression that changes the reason is caught even when the status is unchanged |
| **Out-of-band state inspection** | Repository reads, `get_storage()` reads, direct filesystem reads | The effect (or deliberate non-effect) of the call is visible in the store, not merely reported |
| **Dispatch capture** | A recording stand-in for `celery_app.send_task` | The control plane hands the right task, arguments and queue to the worker boundary |
| **Cross-session probe** | A second `AsyncClient` with its own cookie jar | The two session ids are asserted **different first**, then the isolation assertion is made — so a cookie-sharing regression cannot make an isolation test pass |
| **Measured corpus values** | `build_index` run against the bundled corpora | Partition facts are asserted against measured values, not against restated documentation (see DOC-01) |

## Special Considerations

1. **No Celery broker exists in the test environment, and `celery_app` has no eager mode.** An unpatched `send_task` reaches for `redis://localhost:6379/2` — a real enqueue if the developer happens to have Redis running, a multi-second kombu retry if not. Every module touching `/jobs`, `/models`, `/analyses/*` or `/audio/{id}/variant` therefore carries an **autouse** `fake_broker` patching both `send_task` and `control.revoke`. The 503 and 502 branches are produced by making the stand-in raise, never by hoping a real connection fails.

2. **A custom model can only reach `status="ready"` through the worker.** Two seams are used deliberately: a repository factory for tests that *consume* a ready model, and `validate_custom_model` with a fake `transformers` injected into `sys.modules` for the five cases that verify the *transition itself*. Using the factory for FT-33 would assert the fixture's own capability list rather than the catalogue's — precisely the failure mode of the deleted `test_model_loading_and_initialization`.

3. **`POST /audio/{id}/variant` blocks on `task_handle.get(timeout=45)`.** The stand-in returns a plain callable, so all four sub-cases run in microseconds. Testing the real timeout would be a wall-clock-dependent test and belongs to Section 3.1.4.

4. **The 100 MB / 10 minute limits are verified in two halves.** FT-07/FT-08 shrink the setting to prove the limits are *enforced*; FT-07c asserts the deployed constants are the ones FR-1 names. Together they entail the acceptance criterion; separately neither does. FT-07b covers the boundary, because the interesting defect in a size check is the comparison operator. `MAX_UPLOAD_BYTES` must be set above one 1 MiB read chunk or the first chunk trips the check and the accumulator is never exercised.

5. **Storage and dataset roots are relative paths.** `STORAGE_LOCAL_ROOT` defaults to `"shared-storage"` and `SESSIONS_BASE_DIR` to `"uploads/sessions"`, and `get_storage()` is `lru_cache`d — so a missing fixture both pollutes the working tree and creates order-dependent failures. Every module carries autouse isolation clearing the cache before *and* after, and the execution protocol below verifies the working tree afterwards.

6. **The bundled corpora under `Backend/data/` are gitignored.** Dataset-dependent modules carry a module-level `skipif` so a clean checkout skips rather than errors. The same guard was added to the pre-existing `test_fr10_dataset_extensions.py`, which had none.

7. **`dataset_service._metadata_cache` is a process-global that no fixture clears.** The first read of a bundled corpus probes ~150 audio files. `test_dataset_serving_api.py` carries a module-scoped warm-up so that cost is attributed to the module rather than to whichever test happens to run first. Clearing the cache would make the suite slower, not safer.

8. **The control-plane import-purity check runs in a subprocess.** The pytest process has already imported torch, sklearn and jiwer by collection time, so an in-process assertion could only pass by accident.

| **BUG-12** | **High** | **Fixed** | `app/services/dataset_service.py:73-79, 148-158` | **Cross-session data disclosure.** For a custom dataset the code parsed the owning session out of the qualified name, compared it to the caller's session, logged a warning on mismatch — and then deliberately served the other session's data anyway (`# Use the dataset's session ID instead`; `# For debugging, let's check if the file exists with the dataset's session ID`). Any caller holding a `custom:<sid>:<name>` string could read another session's dataset metadata via `GET /{dataset}/metadata` and download its audio via `GET /{dataset}/file/{path}`. `tests/test_function_testing.py` previously contained 21 tests, of which **13 were removed** as incapable of detecting a defect:

The 5 genuine tests were kept and strengthened (exact messages and exact statuses replacing accept-sets), and the module was rebuilt around FR-1 and the platform surface.

## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.2 is substantively covered for implemented functionality.** Before this pass, three entire routers — custom models, dataset management, dataset serving — had zero automated coverage, and the file nominally responsible for this section could not detect a defect. Every implemented FR in scope now has at least one case bound to its SRS acceptance criterion, and the FR-10 plan's named-but-missing partitioning tests exist at the filename its own manifest reserved.

Deliberately excluded, with justification:

| Excluded | Reason |
|---|---|
| Legacy `/inferences`, `/saliency`, `/perturb` **handlers** | `legacy_sync_enabled` is `False` in every environment, so the routers are never mounted; reaching them requires import-time state no fixture can set. The 410 gate that replaces them is fully covered (FT-22, all four prefixes × two methods, extending the single `/results` assertion that existed before). |
| FR-4 AC-2 (non-empty transcript; probabilities sum to 1) and FR-6's time-support invariant | Worker properties requiring a real model. The *shape* is already asserted by `test_async_jobs.py` with a stubbed adapter; a mocked version here would assert the mock. These are the natural next cases for the opt-in real-model module alongside FT-104. |
| FR-5 clustering and nearest-neighbour acceptance | `test_clustering.py` covers the algorithmic core; 3.1.2 covers the submission contract. |
| FR-9's "higher layers encode more lexical information" | An empirical claim about model internals, already covered by `test_probing_service.py`'s planted-signal recovery; 3.1.2 covers the request contract and label alignment. |
| Real Celery and real Redis integration | Neither service exists in the test environment; requiring them would make this section un-runnable. Dispatch is asserted at the `send_task` boundary, which is where the control plane's responsibility ends. |
| Concurrent writes to the dataset tree | `CustomDatasetManager` has no locking, so two simultaneous uploads read-modify-write the same metadata file. A real defect, but reproducing it needs the injection machinery of 3.1.1's DI-28 for a subsystem with no concurrency control at all — the test would restate the design. **Carried to 3.1.6.** |
| Submission latency budget (FR-4 AC-1's "within the control plane latency budget", FR10plan §9 #18) | A performance criterion; a wall-clock assertion on a shared runner is a flakiness source. **Carried to 3.1.4.** |
| Path traversal on upload filenames, CORS, XSS, CSRF, rate limiting | **Section 3.1.6**, together with the `test_security.py` audit recorded as OBS-07. |
| `S3ObjectStorage` behind the audio routes | A thin boto3 delegate; its key handling is `_safe_key`, covered by Section 3.1.1 (DI-35). |

**Carried forward:** OBS-05 (imbalance flag) to 3.1.3 · OBS-07 (`test_security.py` audit) and dataset-tree concurrency to 3.1.6 · submission latency to 3.1.4 · DOC-01 to the FR-10 plan document owner.
