## Scope note — what "database" means in ECHO

**ECHO has no SQL or document database.** The RUP template's 3.1.1 wording assumes a DBMS with SQL utilities, backup/recovery tooling and a DBA-managed schema. ECHO's persistence tier is instead:

| Tier | Implementation | Module |
|---|---|---|
| Key/value store | Redis 7, three logical DBs, async client, `decode_responses=True` | `app/core/redis.py` |
| Transient control-plane records | Four repositories over Redis DB1, serialised as Pydantic JSON | `app/repositories/*.py` |
| Object store | Local filesystem or S3 behind one abstraction | `app/core/storage.py` |
| Content-addressed cache | SHA-256 digest → Redis pointer (DB0) + object-store payload | `app/worker/executor.py` |
| Custom-dataset tree | Plain JSON files on disk under `uploads/sessions/{sid}/` | `app/services/custom_dataset_service.py` |

The technique objective is therefore reinterpreted, not skipped: *"database access methods and processes"* maps to **key-family correctness, TTL policy, serialisation round-trips, validate-on-read, ownership enforcement, object-key safety, write atomicity, and cache pointer/payload consistency.** Every one of those is exercised below.

This scope reduction is deliberate and is recorded here so the final report does not read as if a DBMS section was omitted.

## Technique Objective

Exercise every persistence access method and process independently of the user interface, so that incorrect target behaviour or data corruption can be observed and logged. Specifically: confirm that data written through the real access methods is populated in the store exactly as intended, that data read back is either faithful or refused, and that no access method silently accepts, produces, or propagates corrupt state.

---

## Technique

The template prescribes two bullets. Each is realised as follows.

**Bullet 1 — "Invoke each database access method and process, seeding each with valid and invalid data or requests for data."**

Every access method is invoked through its real public API — `ensure_session`, `put_queue`/`get_queue`, `cache_result`/`get_result`, the four repositories' `create`/`get`/`get_owned`/`list_owned`/`save`/`update`/`delete`, `LocalObjectStorage.put_file`/`put_json`/`get_bytes`/`download_file`, `analysis_cache_key`/`item_cache_key`/`complete_batch_from_cache`, and `CustomDatasetManager`'s create/add/label methods.

Invalid seeds are injected **directly into the store, out of band**, in the four shapes a real fault produces:

1. Structurally-wrong-but-valid JSON (missing required fields).
2. Syntactically invalid JSON (a truncated write).
3. Empty string (a write truncated to zero bytes).
4. Forged or orphaned index entries (a session index pointing at another session's record, or at a record that has expired).

Object keys are additionally seeded with traversal, absolute and empty values; JSON payloads with non-finite floats.

**Bullet 2 — "Inspect the database to ensure the data has been populated as intended and all database events have occurred properly, or review the returned data to ensure the correct data was retrieved for the correct reasons."**

Assertions are made on **both sides** of every write: the value returned by the public read path *and* the raw store state read out of band (`redis.get`, `smembers`, `zrange`, `ttl`, and direct filesystem reads). This double-sided check is what distinguishes these cases from the pre-existing suite — a return-value-only assertion cannot detect a write that should not have happened, which is exactly the defect DI-22 guards against.

This directly addresses the gap recorded in `currentTest.md`: the pre-existing `test_data_integrity.py` reaches into Redis with **invented key names** (`"test_key"`, `f"session_{sid}"`) that the application never writes. Those tests demonstrate that fakeredis functions; they assert nothing about ECHO. Every case in this section uses the production key helpers and repositories.

## Oracles

Pass/fail is determined automatically — no manual inspection step — by four self-verifying oracle strategies:

| Oracle | How the outcome is observed | Indicates success when |
|---|---|---|
| **Round-trip equality** | Value read through the public API compared to the model written | Parsed model equals the original (compared on the model, never on the serialised string — Pydantic datetime formatting is an implementation detail and asserting the literal JSON is brittle) |
| **Out-of-band store inspection** | `redis.get` / `smembers` / `zrange` / `ttl`, and direct `Path.read_text` | Raw stored state matches the intended key family, index membership and ordering |
| **Expected-exception typing** | `pytest.raises` on the specific exception class, and on `ValidationError.errors()[0]["type"]` | Corruption is refused with the documented exception rather than partially accepted |
| **TTL bounds** | `TTL` compared against `(86_000, 86_400]` (day keys) or `(21_400, 21_600]` (6-hour cache) | Excludes both `-1` (no expiry set) and `-2` (key absent), so an immortal or missing key fails |

The known risk of automated results determination — a test that passes because the property is trivially true — is mitigated by asserting *both* halves of each ownership and monotonicity case (e.g. DI-30 asserts the record **is** findable via `get()` before asserting `get_owned()` refuses it, so a missing record cannot masquerade as a passing access check).

## Special Considerations

Constraints that shaped the implementation and that any future maintainer must respect:

1. **fakeredis has no injectable clock.** It re-stamps `db.time` on every command dispatch, so time cannot be fast-forwarded. Consequently **all TTL assertions are bounds on `TTL`, never observed expiry**, and "expiry mid-job" is simulated with an explicit `DELETE`. `EXPIRE key 0` is deliberately avoided: fakeredis tests `expireat < db.time`, so a zero TTL is not reliably expired on the next command. Shrinking `JOB_TTL_SECONDS` and sleeping is the one approach that would make this suite both slow and flaky — it is not used.

2. **Logical database separation is now mirrored in the test environment.** `tests/conftest.py` originally patched `redis`, `job_redis` and `broker_redis` to a *single* `FakeRedis` instance, so DB0/DB1/DB2 separation was not simulated: a cross-database key collision would have been invisible, and a test could seed a key through the "wrong" client and still pass. The fixture now builds three `FakeRedis` clients on one shared `FakeServer` at `db=0/1/2`, matching production. This was verified against the entire suite before adoption (410 passed, no regressions). Cache-pointer cases additionally seed and read through the same module attribute production code uses (`redis_module.redis`) rather than a locally captured client, so they remain correct regardless of fixture wiring.

3. **`get_storage()` is `lru_cache(maxsize=1)` and `STORAGE_LOCAL_ROOT` defaults to a relative path.** A test that calls it without isolation writes into the developer's real `Backend/shared-storage/`, and the cache turns a missing `cache_clear()` into an order-dependent failure that only appears under some `-k` selections. All filesystem-touching cases are therefore quarantined into one module with two **autouse** fixtures that clear the cache before *and* after. The same hazard applies to `SESSIONS_BASE_DIR` (`uploads/sessions`, also relative).

4. **Minimally sized datasets, per the template's own guidance.** Two- and three-record fixtures throughout; fixed timestamps rather than `datetime.now()` (three successive `now()` calls can collide at float resolution and make ordering assertions arbitrary). The expensive `mock_model_outputs` conftest fixture is never requested — it materialises ~14M Python floats.

5. **Concurrency is forced deterministically, not raced.** `JobRepository.update` is the only optimistic-concurrency code in ECHO. fakeredis 2.23.2 implements WATCH faithfully (per-connection sockets, `Database._watches`, `notify_watch` on write, empty `EXEC` → `WatchError`), so the retry loop is tested against real semantics. The interleaving is injected by a wrapper that performs a competing write on a separate pooled connection immediately before `EXEC`. `asyncio.gather` of two competing updates was rejected as the mechanism: it depends on event-loop scheduling and is the classic test that passes locally and fails in CI.

6. **Corrupt-value handling is deliberately asymmetric between layers**, and the tests encode the distinction. `app/core/redis.py` *degrades*: an unreadable session queue or cached result is logged and treated as absent, because both queue mutators read before writing, so raising would strand the session for the full 24-hour TTL with no recovery short of direct Redis access. The repositories *refuse*: `model_validate_json` raises `ValidationError` for bad syntax and bad shape alike, because silently substituting an empty record would lose a job rather than surface a fault. Neither behaviour is accidental and neither should be made to match the other.

## Findings

Defects observed while executing this section. Each was first reproduced by a failing-if-fixed test, then remediated, then re-verified against the full suite.

| ID | Severity | Status | Location | Finding and resolution |
|---|---|---|---|---|
| **BUG-02** | **High** | **Fixed** | `app/repositories/jobs.py:92` | `record.error = error` was **unconditional**, so any `update()` omitting `error=` wiped an existing error. Compounding it, the terminal-state guard at line 76 only fires when `status` is passed *and* differs — so a `task_id`-only or `child_task_ids`-only update on an already-failed job both mutated it and cleared its reason, leaving `status=failure, error=null`: a failed job with no explanation in the UI. Live call sites doing exactly this: `app/api/routes/jobs.py:159` (immediately after `send_task`), `app/api/routes/analyses.py:140`, `app/worker/tasks.py:145` and `:224`. **Resolution:** the assignment is now guarded by `if error is not None`, and a transition to `success` explicitly clears the error. The second half matters: `app/worker/executor.py:794` records a retryable error and re-raises for a Celery retry, so a bare guard would have left a stale "Retrying batch item" error on the eventual success. No call site needed changing — a survey confirmed `error=` is only ever passed to *set* an error, never to clear one. Guarded by DI-23, DI-24, DI-24b, DI-24c. |
| **BUG-01** | Medium | **Fixed** | `app/core/redis.py:48-60` | `get_queue` and `get_result` called `json.loads` with no error handling; the module had none at all (`RedisError` was imported and never used). A corrupt `sess:{sid}:queue` value therefore bricked `GET /queue`, `POST /queue/add` and `PATCH /queue/progress` for that session for the full 24-hour TTL, since `add_item`/`set_progress` both read before writing — recovery required direct Redis access. **Resolution:** both reads now catch `(JSONDecodeError, TypeError)`, log a warning, and return the canonical default (queue) or `None` (result cache). `get_queue` additionally rejects valid JSON of the wrong type — a stored list would pass `json.loads` and break every consumer downstream. The unused `RedisError` import was removed. Guarded by DI-15, DI-15b, DI-17, DI-21. |
| **BUG-06** | Medium | **Fixed** | `app/services/custom_dataset_service.py:73, 172` | Asymmetric error handling: every *read* path wrapped `json.load` in `try/except`, but `add_file_to_dataset` and `add_manifest_to_dataset` did not, so a corrupt manifest turned a user upload into an unhandled `JSONDecodeError` → HTTP 500 where the routes translate `ValueError` into a 4xx. **Resolution:** both now read through a shared `_read_json_or_raise` helper that logs and re-raises as `ValueError("...unreadable metadata...")`. The read paths deliberately keep their existing degrade-to-absent behaviour — only the mutating paths need to refuse, since they would otherwise write a fresh document over the damaged one. Guarded by DI-50. |
| **BUG-07** | Low | **Fixed** | `app/services/custom_dataset_service.py:59, 119, 187, 292` | Four non-atomic `json.dump` writes with no temp-then-rename, so a crash mid-write left a truncated metadata or labels file — exactly the state DI-49→DI-52 simulate, and one the read paths treat as "dataset absent". **Resolution:** all four now go through a shared `_write_json_atomic` helper that writes to a sibling `.tmp` and `Path.replace()`s it into position, cleaning up the temp file if anything raises. This mirrors the pattern `LocalObjectStorage.put_file` already used. |
| **BUG-03** | Low | **Fixed** | `app/core/storage.py:41-49` | `put_json` called `json.dump` *inside* the `with NamedTemporaryFile(delete=False)` block, so a non-finite float raised before `temp_path` was bound and leaked the temp file into the system temp directory. **Resolution:** the handle is opened and `temp_path` bound before anything can raise, with the serialisation moved inside the `try`, so the `finally` cleanup covers a rejected payload. Guarded by DI-39b. |
| **BUG-04** | Low | **Fixed** | `app/core/storage.py:17-21` | `_safe_key` used `PurePosixPath`, which treats `\` as an ordinary character. A backslash-bearing key was therefore accepted on every platform, after which behaviour **diverged by OS**: on Windows `path_for` caught it via drive-absolute semantics, on POSIX it became a legal single filename. **Resolution:** backslashes are now rejected before parsing. Object keys are always constructed with forward slashes, so a backslash is never legitimate, and the check makes behaviour identical on both platforms — which in turn made this testable (it previously could not be asserted without passing on one OS and failing on the other). Guarded by the `backslash` and `windows_absolute` cases in DI-35. |
| **BUG-05** | Low | **Fixed** | `tests/test_data_integrity.py:135-176` | `TestSessionIntegrity` wrote and read keys named `session_{sid}` — a family the application never writes (the real ones are `sess:{sid}:meta`, `sess:{sid}:queue`, `session:{sid}:jobs\|audio\|custom-models\|jacobian-lenses`). Both tests asserted that fakeredis works, not that ECHO works. **Resolution:** rewritten against the real access methods (`ensure_session`, `put_queue`, `get_queue`), with the isolation test additionally asserting that a session which never wrote sees the empty default rather than a neighbour's data. |
| **OBS-02** | Info | **Fixed** | `tests/test_jacobian_lens.py`, `tests/test_function_testing.py` | Test-environment hygiene, found during the isolation check: both modules `POST /upload` without an `isolated_storage` fixture, so every run wrote real `.wav` files into the developer's `Backend/shared-storage/uploads/{sid}/` and left them there. **Resolution:** both now carry the same autouse `isolated_storage` fixture as `test_async_jobs.py`. Verified: a full-suite run now writes nothing into the real object store. |
| **OBS-01** | Info | **Open — needs a decision** | `app/worker/executor.py:854, 224` | Cache pointers (`analysis-cache:*`, `analysis-item-cache:*`) are written to **DB0** with `JOB_TTL_SECONDS`, while the jobs they serve live on **DB1**. Mixing the session database's namespace with job-lifetime TTLs is a latent operational trap: a `FLUSHDB` against the session DB silently invalidates the entire analysis cache. **Not fixed deliberately** — moving the pointers is a data-migration decision, not a code cleanup: any already-deployed instance would orphan its existing cache payloads on the next release, and the right sequencing (dual-read window, or accept a one-off cold cache) is an operational call. DI-08 locks in that the two databases are distinct so the eventual move is testable. |

**Also changed:** `tests/conftest.py`'s `fake_redis` fixture now mirrors production's three logical databases instead of collapsing them onto one client (see Special Consideration 2). This was validated against the entire suite before adoption.

## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.1 is now substantively covered.** Every persistence access method is invoked with both valid and invalid seeds, and every write is verified on both sides. The pre-existing coverage gap recorded in `currentTest.md` — that no test drove the store through the real API — is closed.

Deliberately excluded, with justification (so the final report can distinguish "not done" from "decided against"):

| Excluded | Reason |
|---|---|
| Queue lost-update race (`queue_service` read-modify-write has no locking) | A real defect, but reproducing it needs the same injection machinery as DI-28/29 for a subsystem with no concurrency control at all — the test would restate the design rather than detect a regression. DI-04 documents the read-modify-write shape; recorded here as a known limitation. |
| Torn mid-`json.dump` writes | Not reproducible without killing the process mid-syscall. Pre-truncating the file (DI-49→DI-52) reproduces the identical on-disk state and is the correct proxy. |
| `path_for` "escapes storage root" branch on POSIX | Unreachable behind `_safe_key` without symlinks; the symlink variant needs a Windows skip and tests the OS more than the code. Confinement is asserted instead. (The backslash route into this branch was closed at `_safe_key` — see BUG-04.) |
| `S3ObjectStorage` | Every method is a thin boto3 delegate; testing it means testing `moto`. `_safe_key` is shared by both backends and is covered, so S3's key handling is covered transitively. |
| Real-Redis integration testing | No Redis service exists in the test environment; requiring one would make 3.1.1 un-runnable in CI. fakeredis 2.23.2's WATCH implementation was verified faithful, which was the only property at risk. |
| Backup / restore / disaster recovery | Belongs to section 3.1.7 (Failover and Recovery), which is currently unimplemented. |

**Carried forward to other sections:** cross-session leakage *under concurrency* (3.1.6); Redis connection loss mid-request and worker-crash-mid-job recovery (3.1.7).

**Open item requiring a decision:** OBS-01 (cache pointers on DB0 with job-lifetime TTLs). This is the only finding from this section left unresolved, and deliberately so — it is a data-migration call rather than a code fix.
