## Scope note

The RUP template divides this technique in two:

> **Application-level security** — an actor can access only those functions or data for which their user type is provided permissions.
>
> **System-level security** — only those actors with access to the system and applications are permitted to access them.

ECHO has no accounts, logins or roles, so there is one user type. Its access-control boundary is the anonymous **session**. Every resource a caller creates (audio, custom datasets, jobs, models, lenses) is owned by the `sid` cookie that created it, and the repository layer refuses it to any other session. For this product, then:

- **Application-level security** means cross-session isolation: a second session can neither read, change nor detect another session's resources.
- **System-level security** means the ways into the system: how a session is issued and what identity it can carry, the cookie's attributes, and which routes are exposed at all. There is no login or remote-access gateway to test.

This report covers the three modules in the `security` category. Isolation of individual resource types is also asserted in 3.1.2 (FT-13, FT-30, FT-38d, FT-77, FT-83, FT-91), and the CORS allow-list and production cookie rules in 3.1.8 (CF-06 to CF-16). Those cases are cited here, not repeated.

Requirements not yet implemented get their own pass and are not traced here.

## Technique Objective

- **Application-level:** a session can reach only its own resources, on every read, write, delete, listing and job submission; a refusal is caused by ownership, not by a broken endpoint; and a refusal reveals nothing about whether the resource exists.
- **System-level:** a session identity is always one the server minted; the cookie carries the attributes that protect it; no unauthenticated administrative or deprecated route is reachable.

---

## Technique

Two in-process clients (`owner`, `intruder`) drive the FastAPI app through httpx's ASGI transport, each with its own cookie jar. The fixture asserts once that their session ids differ, so no case can pass because the two shared a cookie. Redis is fakeredis (the suite's autouse fixture); storage and dataset roots are redirected to `tmp_path`; job dispatch is recorded by a fake `send_task`, so a refused submission can be shown to have dispatched nothing.

## Oracles

These are Member 2's, from `test_access_control.py`:

| ID | Oracle |
|---|---|
| O-1 | **Exact detail.** A denial is checked by status *and* by its exact `detail` string. The datasets router is mounted at the application root as `/{dataset}/metadata`, so almost any mistyped two-segment GET returns some 404; the status alone proves nothing. |
| O-2 | **Paired outcome.** A denial counts only beside the owner's matching success in the same case (`_denied_then_allowed`). A lone 404 also fires when an endpoint is broken, mistyped or removed. |
| O-3 | **Non-disclosure.** "Not yours" must be byte-identical to "does not exist" (`_assert_indistinguishable`), or a response turns an opaque id into an existence oracle. |
| O-4 | **Content, not counts.** A listing is checked for the absence of the other session's ids, not for a length difference. |
| — | **Side effects.** A refused write is followed by a check that the owner's resource is intact, and a refused job submission by a check that nothing was dispatched. |

5. **Identifier and path mismatches in the merged code** (OBS-62). `test_access_control.py` cites the session-id defect as "BUG-13", which is already 3.1.3's Toolbar defect, and points to `tests/plans/3.1.6-security-and-access-control-testing.md`; this report is `3.1.6-security-testing.md` and uses BUG-79. `test_session_cookie.py`'s docstring still says "Test Plan Section 3.1.7". ## Execution Results

Executed on 2026-09-14 and 2026-09-15 on Windows 11 with Python 3.11.9, `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`.

**As merged** (`e8adada`, before any change): SEC-08b detected BUG-79 on six of its seven parameters — `..`, `../escaped`, `a/b`, `../../etc`, non-hex and too long. For each, the forged value came back as the session id (`assert '..' != '..'`). The seventh, `empty`, was unaffected: an empty cookie already falls through `if not sid`. Every other security case held.

**After restoring the check** (BUG-79):

| Run | Result |
|---|---|
| The three security modules | **68 passed** (5.3 s) |
| The same, reverse module order | 68 passed (5.6 s) |
| Inside the full backend suite, forward twice and in reverse module order | 68 of 68 passed in each run |
| `run_tests.py report`, coverage run | Security and Access Control Testing (Section 3.1.6): 68 cases, 68 passed |

`test_access_control.py` was added to the `security` category in `run_tests.py`; TD-01 fails on a module in no category. With it, the backend suite holds 1,071 cases: the 1,039 of Section 5 and the 32 SEC cases.

**The restored check does not affect timing.** It is one regular-expression match per request. To confirm, the `performance`-marked background-workload module and LT-03 were run alternately with the merged `redis.py` (no check) and the restored one, three rounds each under the same host conditions. Neither version did better than the other in any round; LT-03 took 15.35 to 15.65 s on both. Then the whole `performance` run (`pytest tests -m performance`), twice per version, alternating: **71 of 71 passed in all four runs** (130 to 136 s each). The swap was then reverted and the file verified byte-identical to the fixed version.

**Isolation.** `find shared-storage uploads -newer <start> -type f` returned nothing; `git status` lists only the intended changes.

## Findings

### Defects

| ID | Severity | Status | Location | Record |
|---|---|---|---|---|
| **BUG-79** | **High** | **Fixed** (restored) | `app/core/redis.py` `ensure_session` | **A client-chosen session id was adopted verbatim, and it is used as a filesystem path segment.** Found by Member 2 (cited in the test as "BUG-13") and fixed in `d97d9be`; the merge `8dd3b63` dropped the fix, so the merged branch was vulnerable. `SessionMiddleware` takes the `sid` cookie and `ensure_session` accepted any non-empty value. That value names the session's directories (`uploads/sessions/<sid>`, and `datasets/`, `results/` prefixes), so a cookie of `..` or one containing a separator escapes them. The worst case, from reading the code: `POST /upload/dataset/cleanup` calls `cleanup_session_datasets`, which runs `shutil.rmtree(SESSIONS_BASE_DIR / session_id)` — with `sid=..`, the parent of the sessions root, deleting every session's data. Pre-fix: SEC-08b detected it on six parameters, the forged sid coming back as the session id (`assert '..' != '..'`). Two older cases passed throughout (`test_session_fixation_prevention`, `test_invalid_cookie_handling`). **Resolution:** Member 2's check is restored inside the merged function — `if not sid or not _VALID_SID.match(sid): sid = uuid.uuid4().hex` — ahead of the WRONGTYPE recovery, which is kept. Guarded by SEC-08b ×7 and SEC-34. |

## Coverage Assessment and Residual Gaps

**Assessment: application-level security is well evidenced; system-level security is evidenced for session identity and the exposed surface.** `test_access_control.py` holds every denial to three standards: the exact detail, the owner's success in the same case, and a response identical to that for a missing resource. Across audio, custom datasets, dataset serving and jobs, it found and closed the one live defect in the session boundary (BUG-79). That fix had been lost in a merge, and the suite caught it on the first run.

The older modules add little. Of their 36 cases, 4 are evidence (OBS-61). The pattern is the one 3.1.2 found in `test_function_testing.py`: a test that accepts "not found" cannot tell a secure endpoint from a missing one.
