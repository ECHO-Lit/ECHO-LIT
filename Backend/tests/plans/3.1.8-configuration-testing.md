## Scope note

The RUP template describes Configuration Testing as verifying "the operation of the target-of-test on different software and hardware configurations". Its objective is:

> "Exercise the target-of-test on the required hardware and software configurations to observe functional behavior and measure performance characteristics."

**What a configuration is here.** ECHO has no installed client software. It ships one set of images that the SRS requires to run "across environments" under different environment settings. So its configurations are:

- **Hardware:** the accelerator a worker finds: NVIDIA CUDA, AMD ROCm, Apple MPS, or none.
- **Deployment:** each documented way of running the stack, and the environment every process in it receives. That means the code defaults, every compose service with and without `Backend/.env`, the README's GPU and macOS recipes, and the documented production configuration.
- **Storage:** a local shared directory, or an S3-compatible bucket.
- **Image roles:** one Dockerfile builds an API image without the ML runtime and a worker image with it. The scheduler runs in the API image.
- **Client:** the API base the client is built with, the origin the user opens it from, and the browser baseline it is built for.

Each configuration is turned into the input its process really gets, and the SRS is checked under it.

**Items carried into this section.**
- OBS-24 from 3.1.5: the compose file's 7-day TTLs. Resolved by BUG-61.
- OBS-33 from 3.1.7: one worker per queue, and no worker healthchecks. Resolved by BUG-69.

**Decisions taken at planning time**:
- **Scope.** The backend, the deployment files and the client are all in scope.
- **Drift proven by a test is fixed.** Drift between a configuration file and the SRS gets a fix, guarded by that test.
- **`Backend/.env`.** It is wired into compose with `env_file` (`required: false`), and compose pins only container-topology keys. `Settings` keeps reading the process environment only.
- **Production client image.** It takes the API base as a build argument and gains an nginx SPA fallback. Runtime client configuration is recorded (OBS-42).
- **Worker scaling.** Workers become scalable and gain healthchecks. The default topology stays one worker per queue.

## Technique

The template's configuration conditions map onto ECHO as follows.

| Template condition | ECHO realisation | Cases |
|---|---|---|
| Hardware configurations | CUDA, ROCm, MPS, CPU, and mismatched or missing accelerators, produced by patching the torch probes; precision per backend; where attention runs | CF-39, CF-70 to CF-78 |
| Software configurations | The named deployment configurations; local vs S3 storage; the API, scheduler and worker image roles; the client's API base; the browser baseline | CF-01 to CF-05, CF-60 to CF-66, CF-85 to CF-96, CF-100 to CF-110 |
| Configuration-state changes (application settings) | What each environment value does: validated at startup, normalised, or refused; `.env` versus compose precedence | CF-06 to CF-21, CF-30 to CF-37 |
| Other software running alongside the target | Native thread pools that share a prefork worker with Celery; Redis as a shared dependency under a memory bound | CF-44, CF-45 |
| Minimal memory configurations | Model-registry bounds, the Redis `maxmemory` bound, `shm_size` | CF-44, CF-45, CF-79, CF-80 |
| Client workstation configurations | The origin the page is opened from; http versus https API bases; browsers | CF-100 to CF-110 |

**How configurations are produced.** A new instrument module, `tests/_config.py`, turns each configuration file into the environment its process would receive:

- **`service_env(service, dotenv)`** models Compose precedence. The service's `env_file` is applied first, and `environment:` overrides it key by key. An absent file is tolerated only when `required: false`.
- **`interpolate()`** resolves `${VAR}`, `${VAR:-default}` and `$$`. PyYAML's safe loader resolves the merge keys.
- **`read_env_file()`** parses active lines, commented lines, and the production block between `# >>> production` and `# <<< production`.
- **`readme_topologies()`** reads the README's fenced run recipes: which services each `docker compose` command starts, including dependencies and `--scale x=0`, plus the native MPS worker's command and environment.
- **`load_settings()`** clears every Settings key from the environment, sets exactly the configuration's keys, and builds a fresh `Settings()`. The module singleton is never replaced.

**Image roles** are checked in a fresh interpreter (`sys.executable -B -c`). A meta-path blocker refuses the packages the API image does not install and records which file asked for each one, so an import that is caught and ignored cannot hide the attempt.

**S3** runs against stand-in `boto3` / `botocore` modules placed in `sys.modules`. They raise the exception types botocore raises: `ClientError` with a response code, `BotoCoreError`, and `EndpointConnectionError`. boto3 is not installed in the test environment (OBS-43), and no case may reach a network.

**The client** is varied through `vi.stubEnv`, `vi.resetModules` and a dynamic import of `@/lib/api`. The pure resolver is called with each page location. wavesurfer is replaced by a recorder of its `create` options and `load` arguments. The production image and the browser baseline are observable only in source, and those cases say so in their names.

**Every guard was first observed failing** against the unfixed tree. The new modules were written first and run before any fix. Backend: 108 failed and 74 passed. Client: 13 failed and 4 passed. The passes are the characterisation cases listed in Execution Results. Pre-fix evidence is quoted per defect under Findings.

## Special Considerations

**1. Compose semantics are modelled, not executed.** No case builds an image or starts a container; the house convention since 3.1.4 keeps every harness in-process. `tests/_config.py` models the Compose behaviour these files rely on and nothing more: merge keys, `environment:` overriding `env_file`, the long-form `env_file` with `required: false` (Compose 2.24 or later), `${VAR:-default}`, and `$$`. As a one-off static check during implementation, `docker compose config --quiet` parsed the rewritten file and exited 0 without starting anything.

**2. Why the topology keys stay pinned in compose.** A developer's `Backend/.env` is written for native runs: Redis on `localhost`, the object store relative to `Backend/`. Compose now reads that same file. Pinning the four Redis URLs, `STORAGE_BACKEND` and `STORAGE_LOCAL_ROOT` in `environment:` means such a file can tune a container but can never point it at the wrong network or mount (CF-03). This compose file is the local topology, so `STORAGE_BACKEND` is `local` by design. A production deployment is a separate configuration (SAD §7), documented in the production block and checked by CF-05. Two keys beyond topology are pinned deliberately:
- `ML_DEVICE` per worker, because it follows each service's hardware reservation.
- `ENABLE_LEGACY_SYNC_INFERENCE: "false"` on the API, because the legacy routes import torch and the API image does not install it (CF-66, OBS-47).

**3. Settings stay hermetic.** `Settings` never reads a dotenv file (CF-20). Compose injects `Backend/.env` into the containers, and a native run exports it from the shell. If the code read `.env` itself, every pytest run would take its configuration from whichever `.env` the developer happens to have.

**4. The scheduler has no healthcheck.** Celery beat has no remote-control channel to ping. Its fixed `container_name` is kept deliberately, because two beats would publish every periodic task twice (CF-42). The four workers have none, so that they can be scaled (CF-40).

**5. Redis durability choices.** `appendfsync everysec` is retained. It is Redis's recommended trade-off: at most about one second of writes can be lost on power loss. RE-2's concern is eviction under memory pressure, not fsync. The new `maxmemory` bound defaults to `1gb`, and `REDIS_MAXMEMORY` changes it. Redis holds small records and pointers, while results and audio live in the object store. With the bound, a full Redis refuses writes, and the API answers those with a 503 (3.1.7 FO-11), rather than growing until the host OOM-kills it.

**6. Existing developer `Frontend/.env` copies.** Copies made from the old example still pin `VITE_API_BASE_URL=http://localhost:8000`, and so still reproduce BUG-65 from `127.0.0.1`. Deleting that line gives the derived base. The new example leaves it commented.

**7. Accelerator probes are patched.** No single machine has every accelerator. `INFERENCE_RUNTIME` is fixed when `app.core.device` is imported, so the cases call `detect_inference_runtime` directly or patch the module's globals. Where a model is placed is observed through a stand-in whose `.to()` records its target, so no weights are loaded or downloaded.

**8. Subprocesses.** Module CC starts four fresh interpreters: the API role, the scheduler role, the worker role, and the legacy flag. That is the only way to see an image role's import closure unmasked by what the test process already imported. The whole module takes about 13 s. CF-83 in module CD starts one more interpreter to play a pool child, because only a process that has not imported numba yet can show when numba reads its cache setting.

**9. No test reads a developer's `.env`.** Where a `.env` matters, the cases use a synthetic one or the committed example. Vitest would otherwise load `Frontend/.env`, so the client cases stub `VITE_API_BASE_URL` explicitly.

**10. The browser baseline is checked at source level.** Syntax such as `||=` is lowered by esbuild to the build target. Runtime APIs are not polyfilled, so CF-110 denylists the APIs that arrived after the baseline. §3.9.3 names the four browsers without versions; the baseline is therefore Vite 5's default, and CF-109 fails on a Vite major upgrade so that moving the floor is a deliberate decision (OBS-49).

## Coverage Assessment and Residual Gaps

**Assessment: section 3.1.8 is covered for every configuration requirement the SRS states.** Before this pass, one static compose check and six device-selection cases were the only configuration coverage. The section now loads the system's configuration under every documented deployment, hardware, storage, image-role and client configuration, and checks the SRS under each.

The findings share one pattern: configuration that looked set but was not in force. The compose TTLs overrode the SRS (BUG-61). The documented `.env` was never read (BUG-62). The CORS list and worker bounds bypassed validation (BUG-64, BUG-72). The production cookie rules were written in the SRS but enforced nowhere (BUG-63). The S3 configuration had never run (BUG-67).

Two defects are High:
- the deployed stack kept users' audio for a week (BUG-61);
- a fresh worker container could poison its own numba cache and then segfault on every beat-tracking job (BUG-78). This one was found in the running stack, not predicted, and it is the configuration under test (two prefork children) interacting with a library's on-disk cache. Four more stopped the application from working in a documented configuration:
- sessions from `127.0.0.1` (BUG-65);
- the waveform under http (BUG-66);
- storage under S3 (BUG-67);
- worker scaling (BUG-69).

Every defect except BUG-78 was predicted from the code or the configuration files and confirmed by failing guards. BUG-78 was reproduced in the worker container before it was fixed. Every guard is in the suite.

Deliberately excluded, with justification:

| Excluded | Reason | Owner |
|---|---|---|
| Rate limiting (SE-2) | Security and access control | **3.1.6** |
| Runtime client configuration | Decision at planning time (OBS-42) | — |
| The result-backend probe in `/health` | Needs a shared-fixture change (OBS-45) | — |
| Hard-coded limit messages | Would rewrite four existing guards (OBS-48) | — |
