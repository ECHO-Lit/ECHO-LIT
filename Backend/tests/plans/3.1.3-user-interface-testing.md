## Scope note

User Interface Testing verifies a user's navigation through the target-of-test, and that window objects and characteristics conform to standards. The RUP template states the objective as:

> "Verify: Navigation through the target-of-test properly reflects business functions and requirements, including window-to-window, field-to-field, and use of access methods (tab keys, mouse movements, accelerator keys). Window objects and characteristics, such as menus, size, position, state, and focus conform to standards."

This is the first section whose target is the **React client** at `Frontend/`. Sections 3.1.1 and 3.1.2 addressed the Backend, where the product's HTTP API is the external interface; here the target is the interface the researcher actually operates.

Three authoritative sources define what the interface *must be*:

| Source | Role here |
|---|---|
| `docs/Group 16 - AudioLens SRS.pdf` §3.2 (p. 26) | **US-1…US-4** — Learnability, Consistency and standards, Feedback and non-blocking interaction, Error presentation. Stated by the SRS itself "so they can be measured" |
| `docs/Group 16 - AudioLens SRS.pdf` §3.9.1 (pp. 30–31) | **A minimum-element checklist** for the dashboard — the direct oracle for "window objects … conform to requirements" |
| `docs/Group 16 - AudioLens SRS.pdf` §3.12 | "Interface design aims to conform to common web usability and accessibility conventions" — the standards clause the axe cases answer to |

Extract with `pdftotext -layout "docs/Group 16 - AudioLens SRS.pdf" -`. SAD §4's actors and use cases are the same ones 3.1.2 traced to.

**Requirements outside this section's scope.** Requirements not yet implemented are excluded from this section entirely, by decision: they will be tested in their own pass once built. Their absence here is a scoping decision, not a coverage gap, and this document makes no claim about them either way. For §3.9.1 specifically this excludes **waveform zoom**, the **internal word-activation explorer with suppress/amplify/replace controls**, the **job/queue view**, **model-vs-model comparison**, and **saliency/highlighted-span overlays on the waveform** — none of which exists in any form. The traceability matrix below is therefore complete **with respect to implemented functionality**.

**SRS §3.9.3 bounds the section**: "The interface is desktop-oriented." The fixed `h-screen` three-pane layout with `minSize` constraints, and responsive classes in only five files, is therefore **conformant, not a defect**. No case asserts a mobile layout and its absence is not recorded as a gap.

## The state this section found

`Frontend/` had **never had a running test**. `package.json` contained no `test` script and no test tooling of any kind — no vitest, jest, Testing Library, Playwright, Cypress or MSW, in neither `package.json` nor `package-lock.json` nor `node_modules`.

The one file that resembled coverage, `Frontend/src/tests/ui-components.test.tsx` (859 lines, committed as "setup the test suite"), could not execute: it imported `@jest/globals`, `@testing-library/react`, `@testing-library/user-event` and `@testing-library/jest-dom`, none of which were installed. Independently of that, every one of its five suites rendered **locally-defined mock components** declared inside the file — `MockWaveformViewer` (:74), `MockAudioPlayer` (:95), `MockDropZone` (:200), `MockPanelManager` (:384), `MockAttentionVisualization` (:526) — and asserted those. No production component was imported anywhere in it. See "Vacuous tests removed" below.

## Technique

The template's bullets are realised as follows.

**"Navigation … window-to-window, field-to-field."** Module A renders the **real `<App />`** and drives the **real `BrowserRouter`** through jsdom's real history with `window.history.pushState`. This is deliberate: `BrowserRouter` lives inside `App.tsx:17`, not `main.tsx`, so wrapping a *copy* of the route table in a `MemoryRouter` would test the copy — and a copy cannot detect a regression in the real one. UI-04 drives three distinct unknown paths, including `/upload` (an API path, not a route), to pin that nothing shadows the catch-all.

**"Use of access methods (tab keys, mouse movements, accelerator keys)."** Keyboard operation is asserted directly, not assumed: UI-08 completes the whole dashboard ↔ lab round trip with `{Enter}` and no mouse event at all, and UI-34/UI-38 traverse both tab groups with `{ArrowRight}`. Where a control's keyboard behaviour is a platform guarantee rather than product code, the case asserts the *markup that earns the guarantee* — UI-28 asserts a native `<button>`, enabled, focusable and named — rather than synthesising a keypress and thereby asserting jsdom's dispatch.

**"Window objects and characteristics … conform to standards."** §3.9.1's minimum-element list is asserted element by element. §3.12's "accessibility conventions" clause is answered with **axe-core**, and every axe call **names the rules it verifies** — running the full ruleset against a mounted fragment would be close to vacuous, since a fragment is not a page and page-level rules either fire spuriously or pass for the wrong reason.

**Assertion discipline carried from 3.1.2.** Exact strings and exact accessible names; never "it rendered". UI-96 asserts that no message anywhere contains a three-digit status, which an implementation that merely reworded one error could not satisfy.

**Every remediation is guarded, and every guard was observed failing first.** Pre-fix evidence for all 20 defects was captured before any source change and is reproduced in the Findings table.

## Oracles

| Oracle | Observation method | Success indication |
|---|---|---|
| **Accessible name and role** | `getByRole(role, { name })` | The control a user reaches by assistive technology or keyboard exists and is named — not merely that a DOM node is present |
| **axe-core, named rules** | `axe.run` with `runOnly` per case | Zero violations of the specific WCAG rules the case claims; failures print the offending HTML |
| **Route-table network stand-in** | `stubFetch` over `[method, path]` | An undeclared request **throws** `Unrouted request: …`. A permissive mock returning `{}` lets a component silently absorb a shape it never asked for, which is how a crash gets mistaken for a pass |
| **Dispatch capture** | `stub.calls` / `callsFor` | The client sent the right request, or deliberately sent none |
| **Component state machine** | wavesurfer stub as an **event source** with a real listener registry | `WaveformViewer`'s own states, strings and Retry handler are exercised; the stub replaces the Web Audio engine, never ECHO code |
| **Source-level assertion** | `readComponentSource` | Used only where no runtime oracle exists (see Special Consideration 3), and every such case says so in its name |

## Special Considerations

**1. A shared setup file is unavoidable here, and is confined to browser-API shims.** 3.1.1 and 3.1.2 avoid global fixtures on principle. That is not achievable under jsdom: `ResizeObserver`, the pointer-capture methods and `matchMedia` are called by Radix and react-resizable-panels during *mount*, before any test body runs, so there is no per-module seam. `src/tests/setup.ts` therefore contains only absent-API shims, jest-dom and `cleanup` — **no application state, no `fetch`, no `window.confirm`, no component mock**. Everything that changes behaviour is per-module, and `clearMocks`/`restoreMocks`/`unstubGlobals` are all on.

**2. jsdom declares some unimplemented APIs as accessors that resolve to `undefined`.** The first version of the setup file guarded with `if (key in target) return`, which reported `window.matchMedia` as present and skipped the shim — producing a `matchMedia is not a function` TypeError at mount. The guard tests the **value**, not the key. Recorded because the failure mode is silent and easy to reintroduce.

**3. Radix components built on Popper are not assertable under jsdom at acceptable cost.** Measured, with no ECHO code involved: a **bare two-item Radix `Select` takes ~64 seconds to open**; the same open inside the real Toolbar took 87s, and a Radix tooltip's *content* behaves the same way. Radix **Dialog (87 ms), Tabs, Checkbox and Switch (29 ms) are unaffected**, so this is specific to Popper-positioned overlays, not to Radix generally. Consequences, all deliberate:
   - Select **menu content** is asserted at source level, and every such case says "(source-level)" in its name. This is the same device 3.1.2 used for its control-plane import-purity subprocess check: an honest assertion at the only layer where the property is observable, labelled as such, rather than a runtime assertion that cannot be made.
   - Select **triggers** are asserted at runtime — displayed value, accessible name, disabled state — because those need no open menu.
   - Tooltip **content** is asserted at source level; the same hint is asserted at runtime on the drop overlay (UI-47), where it renders inline.
   - Cases must not leave a Popper open: an open overlay keeps the event loop busy and the *next* case pays for it. UI-14 explicitly blurs its tooltip triggers.

**4. A one-shot `ResizeObserver` is worse than a no-op.** An observer that actually delivers a measurement was tried, to settle Radix's popper: the callback re-renders, the re-render re-observes, and the run never terminates. The no-op is correct.

**5. `css: false` changes two assertion families.** Tailwind is not processed under test, so `data-[state=inactive]:hidden` never applies. UI-36 therefore asserts the Fairness panel's continued presence **structurally** (`aria-controls` target still in the document) — `toBeVisible()` is banned there, because it would pass regardless and prove nothing. Second, axe has no computed styles, so `color-contrast` is disabled and colour contrast is excluded from this section entirely.

**6. A fresh `QueryClient` per render is mandatory.** `use-job-query.ts` sets `gcTime: Infinity` on two key families precisely so a 10–30 minute job survives a tab switch. A client shared across tests would carry one test's job status into the next and produce order-dependent passes — the exact failure mode 3.1.2's Special Consideration 5 describes for `lru_cache`.

**7. The network stand-in throws on an unrouted request, and this caught a real mistake.** An early draft used a `"GET *"` catch-all returning `{}`; the dashboard's `/models` handler then called `.filter` on an object and crashed. The catch-all was removed and the dashboard's exact four mount-time requests were measured and declared. A permissive mock would have hidden the crash behind a passing assertion.

**8. Vitest has no marker system.** The `Mk` column in the matrix below is documentation. Selective execution is by file path or `-t` name filter. Recorded so the report does not imply a `pytest -m security` equivalent exists.

**9. Radix supplies the ARIA that ECHO does not write.** Before this section, `grep` for `role=`, `aria-live`, `aria-expanded`, `aria-pressed`, `tabIndex`, `onKeyDown` across `src/` (excluding `components/ui/`) returned **zero matches**. Cases such as UI-35 and UI-44 therefore assert the *library contract as ECHO consumes it*: the value is that a refactor away from Radix, or an `asChild` that discards props, fails here.

**10. The full-app render is the suite's cost centre.** Mounting the dashboard costs 1–5 s and varies with parallelism; a 10 s `testTimeout` proved too tight under `--sequence.shuffle` (UI-91 alone). Raised to 30 s — enough headroom to be stable, short enough that a real hang still fails rather than stalls.

| **US-3's "within 500 ms" acknowledgment budget** | A wall-clock assertion under jsdom measures the runner, not the product. UI-91/UI-92 verify the ordering and non-blocking halves, which a functional test can own honestly | **3.1.4**, with FR-4's control-plane budget |
| **Colour contrast (WCAG 1.4.3)** | `css: false` means axe would evaluate transparent-on-transparent; processing Tailwind would cost every case a PostCSS build for one rule, and jsdom still does not compute cascade like a browser | Real-browser pass; inventory in OBS-15 |
| **Cross-browser behaviour (§3.9.3: Chrome, Firefox, Safari, Edge)** | jsdom is one engine and is not any of the four. A suite implying otherwise would be dishonest | Browser-matrix pass |
| **Real WebGL 2.0 and Web Audio rendering (§3.9.2)** | Declared client platform dependencies precisely because they cannot be emulated. Plotly and wavesurfer are stubbed at the engine boundary; whether a plot is *drawn correctly* is unobservable here | Manual/visual verification |
| **Visual regression, panel pixel geometry** | No CSS is processed and jsdom has no layout engine — every element reports zero dimensions. The RUP "size and position" bullet is covered only semantically (separator roles, collapse state) | Screenshot-diff pass, if commissioned |
| **Radix Select menu contents at runtime** | Measured at ~64 s per open for a bare Select with no ECHO code involved. Asserted at source level instead, and every such case is named "(source-level)" | Real-browser pass |
| **Mobile / responsive layout** | **Conformant, not a defect** — §3.9.3: "The interface is desktop-oriented" | — |
| **CSRF, XSS, session-cookie semantics, `credentials: 'include'`** | Security concerns; 3.1.2 already routed the `test_security.py` audit (OBS-07) there. *Status after 3.1.6 (`3.1.6-security-testing.md`):* cookie semantics covered (SEC-30 to SEC-34); CSRF, XSS and the client's `credentials: 'include'` remain open | **3.1.6** |
| **Backend contract correctness** | Covered end-to-end in 3.1.2 against the real ASGI application. Re-asserting response shapes through a stand-in would assert the stand-in; this suite asserts only what the **client** does with a given response | 3.1.2 |
| **Waveform zoom · word-activation explorer with suppress/amplify/replace · job/queue view · model-vs-model comparison · waveform saliency overlays** | §3.9.1 elements not implemented in any form; excluded from traceability by the standing decision | Post-implementation pass |
